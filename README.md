# ArkPeak

A cozy procedural town-builder — a homage to [*Townscaper*](https://www.townscapergame.com/)
by Oskar Stålberg.

You place coloured blocks on a grid and the town grows around them: walls
connect to walls, roofs cap towers, arches appear where they fit. The
generation is driven by **Wave Function Collapse**, running in Go.

The name comes from **舟山** (Zhoushan): 舟 = boat/ark, 山 = peak/mountain.

## Status

Milestones 1 through 5 are complete:

- **Milestone 1 — Wails v3 scaffold.** The app builds, runs, and the service
  bindings generate cleanly.
- **Milestone 2 — WFC solver.** The solver, the data-driven tile ruleset, the
  propagation, and the entropy selection are implemented and tested.
- **Milestone 3 — static grid.** The island renders as a hexagonal landmass
  over the water, with chunked geometry, a working camera, and a hover
  marker that follows the pointer.
- **Milestone 4 — building.** Clicking places a tile, the backend re-solves
  the neighbourhood, and the frontend applies the diff by rebuilding only the
  chunks that changed.
- **Milestone 5 — procedural geometry.** The tiles are drawn as buildings:
  walls that only show the faces they share, windows with panes, arches with
  a passage through them, and pitched roofs over the buildings.

Not yet done: props, and packaging.

### Trying it out

The town is generated by the backend on launch and rendered as an island of
hexes over the water. Pick a layer and a tile from the palette, then click a
cell to build. The solver re-solves the neighbourhood and the town grows
around what you placed. Right-click a cell to take your constraint back.

If a placement cannot work, the game says why in plain words — "a roof needs
something to stand on" — rather than showing a solver error.

## Requirements

- Go 1.26 or newer (the `go.mod` asks for it; `GOTOOLCHAIN=auto` will fetch it)
- Node 20 or newer
- Wails v3 CLI: `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0`
- Task: <https://taskfile.dev>

On Linux you also need the Wails build dependencies (GTK 4 and WebKitGTK 6):

```sh
sudo apt install libgtk-4-dev libwebkitgtk-6.0-dev build-essential
```

## Running it

### From a fresh clone

```sh
git clone <repository-url> arkpeak
cd arkpeak

# 1. Install the frontend dependencies.
npm install --prefix frontend

# 2. Generate the TypeScript bindings from the Go services.
#    (They are gitignored, so a fresh clone has none.)
wails3 task bindings

# 3. Run it.
wails3 dev
```

Step 2 is only needed once. `wails3 dev` regenerates the bindings on every
start, so `wails3 task bindings` is for a fresh clone or after changing a
service method's signature.

### The usual commands

```sh
wails3 dev          # hot-reloading development build
wails3 task check   # Go tests, frontend typecheck and lint
wails3 package      # distributable build
```

The `wails3` CLI must be on your `PATH`; the Taskfile shells out to it.

### Building without the dev server

```sh
npm run build --prefix frontend   # builds frontend/dist
go build -o bin/arkpeak .         # embeds frontend/dist into the binary
```

## How it fits together

```
internal/wfc/     The solver: grid maths, tile rules, propagation, collapse.
internal/town/    The town: authoritative state, constraints, save/load, the
                  Wails service, and the tile ruleset as JSON.
frontend/src/     The renderer: Three.js scene, camera, input, palette, HUD.
```

The split is deliberate: **the solver never knows about rendering, and the
renderer never decides what a cell contains.** The backend owns the truth;
the frontend draws it and asks for changes.

### The WFC solver

The grid is a **hexagonal** island in axial coordinates `(q, r)` with a
separate vertical axis, `layer`. A radius-24 island holds 1801 cells per
layer. Each cell starts in superposition with every tile valid for its
layer, and collapses to one.

The island is a hexagon rather than a rectangle because a rectangle in axial
coordinates is a rhombus on screen, which reads as a skewed slab. The
hexagon gives the solver a natural boundary and the player a landmass.

The rules are **data, not code**. `internal/town/rules/town_rules.json` lists
the tiles, the connector on each of their six edges, and the connector pairs
that may meet:

```json
{
  "id": "window",
  "weight": 7,
  "layer": "0",
  "edges": { "n": "window", "ne": "wall", "se": "wall", "s": "wall", "sw": "wall", "nw": "wall" },
  "up": "wall",
  "down": "any"
}
```

Two tiles may touch when their facing connectors form a compatible pair. The
special connectors `any` (matches everything) and `nothing` (matches
nothing) keep the rules expressive without enumerating every pair.

The solver propagates constraints with a queue, picks the cell with the
fewest remaining candidates, and collapses it with a weighted random choice.
Cells that are left with a single candidate are settled immediately and
propagate in turn, so a constraint ripples through a whole building.

**Determinism.** Each cell's random choice is derived from the town's seed
and the cell's coordinates, so the same constraints always produce the same
town, and a regional re-solve is reproducible regardless of solve order.

**Layers are chained.** The town is solved from the ground up: layer 1 is
solved against the layer 0 tiles beneath it, so a roof can never float above
an empty plot.

### State updates: pull, not push

Mutating methods return a `GridDiff` describing exactly which cells changed,
so the frontend applies it immediately without a second round trip. A push
model (`app.Event.Emit("town-updated", diff)`) is available if a second
window ever needs to follow the first, but a single window does not need it.

### Saving

A saved town stores only the seed and the player's constraints, in the order
they were placed. The settled cells are derived by replaying those
constraints, so a save file stays small and a loaded town is identical to the
one that was saved.

## Mirroring Go types in TypeScript

The Go structs in `internal/town/types.go` are the source of truth. Wails
generates TypeScript for them, and `frontend/src/types.ts` re-exports those
generated types so the rest of the frontend never depends on the generated
file's long, module-path-derived location:

```ts
export type { Cell, GridDiff, TileInfo, TownSnapshot } from "../bindings/github.com/incurl/arkpeak/internal/town/models";
```

The hand-written unions in that file (`TileType`, `ColorName`) cannot be
generated by Wails, so they are kept in sync with the ruleset by hand. The
generated bindings live in `frontend/bindings/` and are gitignored — run
`wails3 task bindings` to recreate them.

## Rendering

The town is split into **chunks** of 8×8 cells. A change to a few cells
rebuilds only the chunks that contain them, rather than the whole town. The
partition is checked at startup (`verifyChunkPartition`), because
`chunkOf` and `chunkCells` must agree exactly or a cell is drawn into a
chunk that is never rendered and silently disappears.

The frontend keeps a mirror of the backend's grid and a set of dirty chunks.
Applying a diff marks the chunks that changed; the render loop drains that
set, so a frame where nothing changed does no work at all. A click on a
3602-cell town rebuilds one chunk, not forty.

### The geometry follows the rules

A tile is drawn according to what it is *and* what it touches. A wall only
draws the faces it shares with another wall, so a building reads as a solid
volume rather than as a stack of hexagons. A window adds a pane. An arch
leaves a passage through the cell.

Two different questions are answered separately:

- **May these cells touch?** That is the solver's rule, and it comes
  straight from the ruleset's connector table.
- **Do they form a continuous surface?** That is the drawing rule, and it
  needs both sides to declare a real connector. An arch, whose other sides
  are wildcards, does not grow a wall towards an empty plot.

The connectors are sent to the frontend with the snapshot, so the rules are
never restated in TypeScript. They are checked at startup
(`verifyConnectorTables`), because a mismatch would make the geometry stop
matching the town, quietly.

An upper storey is only drawn where the ground beneath it is solid. Without
that, the whole island would be covered by a sheet of roof.

The geometry is cached by tile and neighbour pattern, so the ~2300 cells of
a town share about a hundred distinct geometries.

### Layers

Each tile belongs to a layer: a wall sits on the ground, a roof on the storey
above. The player picks the layer in the palette, and a click lands on that
layer. The active layer is never changed by moving the pointer, so the
choice stays the player's.

The backend sends the layer of every tile alongside its id
(`TownSnapshot.tileInfo`), and `CanPlace` explains a refusal in plain words
before the placement is attempted.

### The solver keeps the neighbourhood still

A regional re-solve asks every cell in the region to keep the tile it
already has. That request is honoured outright: a cell that still *can*
hold its tile keeps it, rather than being collapsed at random. Without
that, every re-solve had a small chance of reshaping a cell, and over a
play session the town would slowly rewrite itself.

The request is given up only when the tile is genuinely impossible, so the
player can still paint the town into a corner and have the solver sort it
out.
